# Cloudflare setup (no live account in this lab — exact settings for a real one)

This lab has no Cloudflare account attached; this document is the settings a real
deployment needs, so the app tier sits behind Cloudflare's proxy/load-balancer
instead of being directly internet-facing.

## DNS records

- `A`/`AAAA` records for each app host (or a single record if using a Cloudflare
  Load Balancer origin pool — recommended), **proxied** (orange cloud), not "DNS
  only" — the point of Cloudflare here is the proxy layer, not just DNS.

## Origin pool + health checks (Cloudflare Load Balancing)

- Create an **origin pool** with each app host (`app1`, `app2`, `app3`) as an
  origin, weighted evenly unless capacity differs.
- **Health check**: HTTP(S), path `/health` (the same endpoint HAProxy's own
  `app_be` backend already uses — see `haproxy/templates/haproxy.cfg.tmpl`),
  expected status `200`, interval 60s, retries 2, timeout 5s.
- **Load balancer**: attach the pool, steering policy "Off" (round robin) unless
  you have a reason for geo-steering, session affinity off (the app tier itself
  is stateless — sessions/state belong in Redis, not sticky routing).

## Real-IP restoration

Cloudflare's proxy replaces the client's real IP with its own at the TCP layer;
the original IP arrives in the `CF-Connecting-IP` header. Nginx needs to trust
that header only from Cloudflare's own IP ranges, or any client could spoof it.

Add to `apps/php/nginx.conf` (or your production Nginx config, generated by the
`haproxy`/app-tier Ansible role if you extend it to manage Nginx directly):

```nginx
# Cloudflare's published IPv4/IPv6 ranges: https://www.cloudflare.com/ips/
# (fetch and template this list rather than hand-copying it -- it changes)
set_real_ip_from 173.245.48.0/20;
set_real_ip_from 103.21.244.0/22;
# ... the rest of Cloudflare's published ranges ...
real_ip_header CF-Connecting-IP;
```

HAProxy itself, sitting behind Nginx/the app tier in this topology, doesn't need
this — it only ever sees traffic from your own app tier, not directly from
Cloudflare. If HAProxy's `app_fe` frontend were instead the direct Cloudflare
origin (an alternative topology to putting Nginx per-app-host in front), add the
same real-IP trust there via `http-request set-header` + `src` ACLs restricted to
Cloudflare's ranges, since HAProxy doesn't have Nginx's `set_real_ip_from`.

## Firewall rules — only allow Cloudflare to reach the app tier

The app tier's public-facing port should refuse anything that isn't Cloudflare.
On each app host (the `common` Ansible role's UFW baseline is the starting
point — add these on top):

```bash
# Fetch Cloudflare's current ranges (do this in Ansible, not by hand -- they change):
#   https://www.cloudflare.com/ips-v4/  and  https://www.cloudflare.com/ips-v6/
for cidr in $(curl -s https://www.cloudflare.com/ips-v4/); do
  ufw allow proto tcp from "$cidr" to any port 80,443
done
ufw deny 80
ufw deny 443
```

The database tier (HAProxy's `:5000/:5001/:3307/:3308`, the db hosts themselves)
should never be reachable from the internet at all, Cloudflare or otherwise — see
the README's "Production checklist".

## Putting this in Ansible

If you want this automated rather than a manual one-time setup: add a
`cloudflare` role that uses the `cloudflare.cloudflare` collection's
`cloudflare_dns`/`cloudflare_load_balancer` modules (or the Cloudflare API
directly via `ansible.builtin.uri`) to manage the origin pool and DNS records
from `group_vars`, and a handler that re-fetches Cloudflare's IP ranges and
re-renders the UFW rules above on a schedule (they do change, infrequently).
That role isn't included here since it needs a real Cloudflare account and API
token to test against, which this lab doesn't have.
